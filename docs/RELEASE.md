## 今後の変更

1. mainから作業ブランチを作り、対象の変更を実装する。
2. `npm ci`、`npm test`、本番向けビルドを確認する。テストでは実サービスに保存・通知・AI生成をしない。
3. 差分を確認してGitへコミットし、GitHubで管理する。push前にCloudflareの自動配備条件を確認する。
4. 本番反映の対象・差分・未確認事項を確定し、承認済みの範囲で配備する。
5. GASを変更する場合は、フロントとの互換性を検証する。保存v2はGASのバージョン16以降が必要なため、今回と同じ構成ではGASを先に配備する。手順は下記「GASとフロントを続けて反映する」に従う。
6. 反映後、HTML・JS・CSSとGASの公開バージョンを確認し、`releases/`に記録する。
7. 対応するコミットに新しい公開版タグを付ける。既存の公開版タグは移動させない。

公開記録には、配備日時、Gitタグ、Workerバージョン、GASバージョン、静的アセットのハッシュ、復元先、実施した検証と未確認事項を含めます。秘密情報や診断回答者の情報は記録しません。

## GASとフロントを続けて反映する

新GASは旧画面のAI呼び出しを拒否し、旧GASは新画面にAI利用証明を返しません。切り替え中はAIが使えないため、次の順で間を空けずに行います。保存はどちらの組み合わせでも動きます。

1. **事前（本番に影響なし）**：`.env.production.local`等に公開用の`VITE_TURNSTILE_SITE_KEY`を設定し、`npm run build:release`で公開用ビルドと検査を済ませる。失敗したらここで止まり、本番は変わらない。
2. **GASプロパティ**：`TURNSTILE_SECRET_KEY`・`AI_SESSION_SECRET`と、必要なら上限値・`CLAUDE_MODEL`を設定する（既存の公開版16は新しいプロパティを読まないので影響しない）。
3. **GAS反映**：Apps Scriptの「デプロイを管理」で既存のWebアプリを編集し、新しいバージョンを選ぶ（URLを変えない）。マニフェストの`oauthScopes`により権限の再承認画面が出た場合は、スプレッドシート・メール送信・外部通信の3つだけであることを確認して承認する。
4. **直後にフロント反映**：`npm run deploy:built`。手順1で検査済みの`dist`を再ビルドせずに配備する（ここで作り直さないため、ビルド失敗で停止時間が延びない）。
5. **確認**：`npm run healthcheck -- --require-security-headers`、実画面の表示、承認済みの検証データでの保存・AI。

ロールバック：画面だけ戻す場合は前のWorkerバージョンへ戻す（新GASは保存v2を受け付けるので保存は続く。旧画面のAIは使えない）。GASも戻す場合は、GASの公開バージョンを前に戻してから画面を戻す。

## 復元の注意

本番の復元も本番操作です。GitのcheckoutだけではCloudflareやGASは切り替わりません。

画面だけを以前のWorkerバージョンへ戻す場合、GAS16は旧`save_only`にも対応しています。次回反映用のGASは旧`save_only`を受け付けません（2026-10-19版の画面は保存v2を使うため影響なし）。GASも15へ戻す場合は、保存v2を使う画面との不整合を避けるため、画面を先に戻します。既存の回答や送信ID列は削除しません。

`test/fixtures/Code.v15.gs`は互換性テスト用で、運用上の復元を自動実行するファイルではありません。
